# 1. 基本原则

- 单一职责：UI 只负责展示与用户交互；Hub Core 负责调度；Content Script 负责媒体执行。
- 明确边界：桌面 Host 只做命令输入与状态展示（可选），不做网页媒体逻辑。
- 最小状态：只持久化必要配置（如用户选择的 active tab）。
- 可观测性：关键路径必须可定位（连接状态、命令成功/失败原因）。

# 2. TypeScript 约定

- 所有跨模块消息必须有明确类型定义（UI<->SW、SW<->CS、SW<->Desktop）。
- 协议字段：
  - `type/name/id/replyTo/payload` 必须统一
  - `payload` 使用结构化对象，不传递函数与 DOM 引用
- 禁止隐式 any。

# 3. 命名与目录

- 文件按职责分层：`ui/`、`sw/`、`content/`、`shared/`。
- 命名规则：
  - 消息名使用 PascalCase：`PlayPause`, `State`
  - 内部方法使用 camelCase：`selectActiveTab`

# 4. 错误处理规范

## 4.1 不允许吞错误

- 任何命令执行失败必须返回明确失败原因（字符串即可）。
- Native Messaging 侧：
  - stdout 仅输出协议消息
  - 错误/日志输出到 stderr（桌面侧）

## 4.2 失败回执格式

UI/SW/CS 与 Desktop 协议都统一使用：

```json
{ "ok": false, "message": "..." }
```

# 5. 通讯规范

- Native Messaging 协议规范以 [08-NativeMessaging协议规范.md](./08-NativeMessaging协议规范.md) 为准；[03-通讯协议-NativeMessaging.md](./03-通讯协议-NativeMessaging.md) 为概览摘要。
- 需要新增命令/事件时：
  - 先补文档（name、方向、payload schema、错误语义）
  - 再补类型定义（shared/types）
  - 最后实现两端处理

# 6. 状态上报节流

为避免性能问题：

- Content Script 上报 `position` 必须节流（例如 1s 一次或更低频）
- 元数据变化与播放状态变化可即时上报

# 7. 测试与验证（建议）

- 单元测试：
  - active tab 选择策略
  - 消息路由与请求/响应关联
  - 协议编码/解码（桌面侧 framing）
- 手动验证清单：
  - 多 Tab 同时打开媒体页：active 选择正确
  - 桌面触发命令：扩展能及时响应并回执
  - tab 关闭/刷新：状态清理正常

# 8. 文档同步要求

任何新增模块/协议变更必须同步更新 /doc：

- 架构图或数据流变化：更新 01
- 模块职责变化：更新 02
- 协议变化：更新 03
